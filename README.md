# Ledger Eyes

Ledger Eyes reads what the crypto crowd writes and turns it into one small, fixed-format result file, the **brief** (`brief.json`). The brief is the interface: other programs read it, not the notebook.

The work is a single Jupyter notebook that runs from top to bottom on Google Colab. It uses the public StockTwits crypto dataset from Hugging Face and needs no keys or accounts.

Chapters so far: 0 The question and the data · 1 Loading · 2 A first look · 3 Cleaning · 4 Tokenization · 5 Training, validation and test sets · 6 Vectorization · 7 Models · 8 Evaluation · 9 Topics · 10 Why · 11 The brief: format, check, save and panel. Chapters 4 to 8 tell bullish from bearish posts and fill the brief's `sentiment` section; chapter 9 sorts posts into topics and fills the `topics` section; chapter 10 crosses the two (which topics lean bullish, which lean bearish), calibrates the model's bullish share with its recognition rates from chapter 8, and fills the `why` section. Chapter 11 checks the brief against its fixed format (see [docs/brief-format.md](docs/brief-format.md)), saves it, and shows its main tables on a small panel that reads only the saved file.

## Run on Google Colab

1. Open <https://colab.research.google.com>, choose *File → Upload notebook* and pick `notebook/ledger_eyes.ipynb`.
2. Optionally change the switches in the first code cell.
3. Choose *Runtime → Run all*.

The first code cell after the switches installs the packages Colab lacks (for example `emoji` and `contractions`, and `gradio` for the panel when Colab does not have it); everything else, including TensorFlow/Keras and Hugging Face `tokenizers`, is preinstalled on Colab, and a package that is already there is left as it is. The same cell sets `GRADIO_ANALYTICS_ENABLED=False` before anything is imported, so Gradio sends no usage statistics and makes no version checks. The data is read straight from Hugging Face (`hf://datasets/ElKulako/stocktwits-crypto/st-data-full.xlsx`), and the brief is saved to `data/brief.json` inside the Colab session.

The last cell starts the panel (`LAUNCH_PANEL = True`, the default): a small Gradio page with four tabs (what the brief covers, the evaluation table, the topic table, the topic × bullish table), read from the saved `brief.json`. It never asks for a public link (`share=False`) and listens only on the notebook's own machine (`127.0.0.1`); Gradio shows it below the cell.

The notebook has not yet been run on Colab itself (so neither has the panel); it has been run locally with the same code path, including reading the `hf://` address directly.

## Switches

All switches are in the notebook's first code cell (tag `parameters`), one plain assignment per line, each with a comment of the form `# default: ...; ...`. Results are reported with the defaults. A switch whose comment says `two-state, other: X` has exactly two values; the quick check flips all of them together to `X` for its second run, so a new two-state switch joins that run automatically. `LAUNCH_PANEL` also has two values but is deliberately not marked two-state: the checks never start the panel.

| Switch | Default | Other values | Meaning |
| --- | --- | --- | --- |
| `DATA_SOURCE` | `hf://datasets/ElKulako/stocktwits-crypto/st-data-full.xlsx` | a local `.xlsx` path with the same layout | Where the posts come from. |
| `WORK_DIR` | `data` | any folder | Cache and saved brief. |
| `RANDOM_SEED` | `42` | any integer | Seed for the working sample. |
| `SAMPLE_PER_CLASS` | `50000` | any positive integer | Most posts per class in the working sample. |
| `N_CLASSES` | `2` | `3` (two-state) | 2 = bearish vs bullish; 3 adds neutral. |
| `BTC_ONLY` | `False` | `True` (two-state) | Working sample only from posts that mention Bitcoin. |
| `EMOJI_TO_WORDS` | `True` | `False` (two-state) | Turn emoji into English words instead of deleting them. |
| `KEEP_NEGATIONS` | `True` | `False` (two-state) | Keep not, no, never, nor (and the n't forms) out of the stop word list. |
| `BPE_VOCAB_SIZE` | `5000` | any positive integer | Target vocabulary size of the subword (BPE) tokenizer of chapter 4. Every single character seen in training and the 5 special tokens are always kept and merged pieces are added up to this size, so the vocabulary is smaller when a small sample has fewer pairs to merge, and larger (with nothing merged) when the value is below the number of single characters plus special tokens. Display only. |
| `VOCAB_SIZE` | `1000` | any positive integer | Most words each vectorizer of chapter 6 keeps (as in the course). |
| `EPOCHS` | `5` | any positive integer | Passes over the training set in chapter 7 (as in the course). |
| `BATCH_SIZE` | `50` | any positive integer | Posts per training step in chapter 7 (as in the course). |
| `TOPIC_SCOPE` | `"btc"` | `"all"` (two-state) | Posts of the topic table of chapter 9: every post that mentions Bitcoin, or posts about all coins. All three classes either way; `N_CLASSES` and `BTC_ONLY` do not apply. |
| `TOPIC_MAX_POSTS` | `100000` | any positive integer | Most posts in the topic table. When more posts are in scope, a random draw with `RANDOM_SEED` keeps this many. The default keeps every Bitcoin post of the full dataset; with `"all"` it draws 100,000 of all posts, and a value above the number of posts takes every post (with `"all"` on the full dataset that is about 1.3 million posts, and the whole notebook then runs about three times as long). |
| `N_TOPICS` | `8` | any positive integer | Number of topics (KMeans groups) in chapter 9. When the topic table has fewer distinct post vectors than this, it gets as many topics as it has distinct vectors. |
| `BULLISH_THRESHOLD` | `0.7` | any number from 0 to 1, not below `BEARISH_THRESHOLD` | Chapter 10: a post whose probability of bullish is at or above this counts as bullish by the model. |
| `BEARISH_THRESHOLD` | `0.3` | any number from 0 to 1, not above `BULLISH_THRESHOLD` | Chapter 10: a post at or below this counts as bearish; between the two thresholds it is unsure. When both are equal, a probability equal to them counts as bullish. A bearish threshold above the bullish one stops the notebook at the switch check. |
| `MIN_TOPIC_POSTS` | `200` | any positive integer | Chapter 10 marks a topic with fewer posts than this as having too few posts (`1` marks none). |
| `MIN_RATE_GAP` | `0.2` | any number from 0 to 1 | Chapter 10 calibrates the bullish share (see **Why** under [Interface](#interface)) only when the model's two recognition rates, measured in chapter 8, are at least this far apart: the true bullish rate (bullish recall) minus the false bullish rate (1 − bearish recall), which equals bullish recall + bearish recall − 1. A model that guesses has a gap of 0, a perfect one a gap of 1; a gap of 0 or below is never enough, whatever the switch says. Why 0.2: calibration divides by the gap, so every error of the counted share (chance, or the rates themselves being measured on a few hundred test posts) is multiplied by 1 ÷ gap. 0.2 allows at most a five-fold magnification, so an error of 2 percentage points in the counted share becomes at most 10 points, the size of the chance band that `MIN_TOPIC_POSTS` already accepts for about 100 bullish or bearish posts; it is the same as asking for a balanced accuracy (the mean of the two recalls) of at least 60%. A rule of thumb, not a statistical test. A value outside 0 to 1 stops the notebook at the switch check. |
| `MIN_BULLISH_BEARISH_POSTS` | `100` | any positive integer | Chapter 10 marks a row (every topic and the overall row) whose bearish + bullish posts by label are fewer than this (`too_few_bullish_bearish`; `1` marks none). The mark changes no number. Why 100: a share rests on its bullish and bearish posts, and 100 is where the 200 of `MIN_TOPIC_POSTS` comes from (about half of the posts neutral, leaving about 100 bullish or bearish ones). A value that is not a positive integer stops the notebook at the switch check. |
| `LAUNCH_PANEL` | `True` | `False` (not two-state; both checks always use `False`) | Chapter 11's last cell starts the panel (`True`) or only builds it (`False`). Any other value stops the notebook at the switch check. |

## Interface

These names are fixed; later chapters build on them.

| Name | Meaning |
| --- | --- |
| `df_all` | Every post of the data source. Created in chapter 1 and kept unchanged until the end of the notebook; no later cell may drop or overwrite it. |
| `df` | The working sample drawn in chapter 2 (see below). |
| `post_id` | Stable id of a post: `<sheet name>:<row number in the sheet>`, for example `stocktwits_1:2` for the first post of the first sheet (row 1 holds the column names). Unique in `df_all`, derived from the position in the file and never from random numbers, so the same data source gives the same ids on every run. `df` and every later table carry it. Ids are only comparable between runs on the same data source. |
| `text` | The original post text. A cell that pandas reads as empty becomes an empty string; in the full file these are 59 formula cells (see [Known limitations](#known-limitations)). |
| `label` | 0 = bearish, 1 = neutral, 2 = bullish. The meaning never changes, also not in the working sample. |
| `mentions_btc` | `True` when the text contains `bitcoin` or `btc` as a whole word, ignoring case (regular expression `\b(?:bitcoin\|btc)\b`). "bitcoin's" counts; "bitcoins", "gbtc" and "btc_usd" do not. |
| `clean_text` | Column of `df` only: the text after chapter 3's cleaning. |
| `clean_texts(texts)` | Cleans a column (or list) of raw texts with the current switches and returns a pandas Series (same index when given a Series). It runs the same step functions as chapter 3's step-by-step cells, in the same order; the notebook checks that both give identical results. |
| `brief` | The result dictionary, saved to `{WORK_DIR}/brief.json` by the last cell. |
| `CLASS_LABELS` | Labels in use, in order: `[0, 2]` with two classes, `[0, 1, 2]` with three. Every class table and every probability array follows this order. |
| `train_df`, `val_df`, `test_df` | Training (80%), validation (10%) and test (10%) parts of `df`, split in chapter 5, stratified by label, with `RANDOM_SEED`. They keep all columns of `df`. |
| `train_post_ids` | `frozenset` of the `post_id`s in `train_df`. A post whose id is not in it was never seen by the models during training. |
| `count_vectorizer`, `tfidf_vectorizer` | Chapter 6's vectorizers, fitted on `train_df["clean_text"]` only (also in the dict `vectorizers`, keys `"count"` and `"tfidf"`). |
| `models` | Chapter 7's networks: `{"count_network": {...}, "tfidf_network": {...}}`, each with `model` (the Keras model), `vectors` (`"count"` or `"tfidf"`) and `history`. |
| `selected_model_name`, `selected_model`, `selected_vectorizer` | The model chosen by macro-F1 on the validation set, and the vectorizer it reads. |
| `sentiment_proba(cleaned_texts)` | Class probabilities from the chosen model for any batch of **cleaned** texts (a list or pandas Series of strings; clean raw posts with `clean_texts` first; a missing value counts as an empty text). Returns a NumPy array of shape `(number of texts, number of classes in use)`; every row adds up to 1; an empty input gives shape `(0, number of classes)`. Column order is fixed and stored in `SENTIMENT_PROBA_LABELS`: two classes `[0, 2]` = [bearish, bullish]; three classes `[0, 1, 2]` = [bearish, neutral, bullish]. |
| `SENTIMENT_PROBA_LABELS` | The label of each column returned by `sentiment_proba` (equal to `CLASS_LABELS`). |
| `BULLISH_COLUMN` | Index of the "probability of bullish" column: always the last one (1 with two classes, 2 with three). |
| `topic_posts` | Chapter 9's **topic post table**: the posts in `TOPIC_SCOPE` taken from `df_all` (not from the working sample), all three classes in their natural shares, at most `TOPIC_MAX_POSTS` of them, in file order. Columns: `post_id`, `text`, `label`, `mentions_btc`, `clean_text` (cleaned with `clean_texts`) and `topic`. One row per post; `post_id` is unique. |
| `topic` | Column of `topic_posts`: the topic number of the post, an integer from 0 to the number of topics − 1 (KMeans' own numbering, the same as `topic_model.labels_`). Every post has one. |
| `topic_vectorizer` | Chapter 9's own `TfidfVectorizer`, fitted on all of `topic_posts["clean_text"]`; `None` only in the corner case where no post has a single word left. |
| `topic_model` | The fitted `KMeans` model (its `cluster_centers_` are the topic centres); `None` when no clustering was needed (no post, or no word at all). |
| `topic_table` | One row per topic (index `topic`): `name`, `posts`, `share`. The quotes are in `brief["topics"]["topics"]`. |
| `why_posts` | Chapter 10's table, one row per post of `topic_posts`, same order: `post_id`, `label`, `topic`, `bullish_proba` (the chosen model's probability of bullish), `model_call` (`"bullish"`, `"bearish"` or `"unsure"`), `half_call` (`"bullish"` or `"bearish"`, split at 0.5), `seen_in_training` (`post_id` in `train_post_ids`) and `in_fair_comparison` (not seen in training and labelled bearish or bullish). `topic_posts` itself is not changed. |
| `bullish_probability(proba)`, `model_call(probability)` | Turn `sentiment_proba`'s output into the probability of bullish (two classes: the bullish column; three classes: bullish ÷ (bullish + bearish), 0.5 when both are 0), and that probability into a call: bullish at or above `BULLISH_THRESHOLD`, otherwise bearish at or below `BEARISH_THRESHOLD`, otherwise unsure. `MODEL_CALLS` lists the calls in order. |
| `half_call(probability)` | The call at 0.5 used for calibration: `"bullish"` when the probability of bullish is above 0.5, otherwise `"bearish"` (exactly 0.5 is bearish); nothing is unsure. With two classes it gives exactly the labels chapter 8 evaluated for the chosen model (chapter 10 checks this on the test posts). `HALF_CALLS` lists the calls in order. |
| `calibration_rates` | The recognition rates for the calibration, a dict: `status` (`"applied"`, `"rates_missing"`, `"rate_gap_too_small"` or `"three_classes"`), `model` and `subset` (the row of chapter 8's evaluation table they come from: the chosen model, `"test_mentions_btc"` with `TOPIC_SCOPE = "btc"`, `"all_test"` with `"all"`), `true_bullish_rate` (bullish recall), `false_bullish_rate` (1 − bearish recall), `rate_gap` (their difference; the three are `None` with three classes or when a recall cannot be computed) and `rate_posts` (that row's bearish and bullish test posts, keys `"0"` and `"2"`). |
| `calibrate_bullish_share(share, rates=None)` | Calibrates a bullish share counted with `half_call`: (share − false bullish rate) ÷ (true bullish rate − false bullish rate), clipped to [0, 1]. `None` when `share` is `None` or the status of `rates` (default `calibration_rates`) is not `"applied"`. |
| `why_row(posts)` | Every field of one row of the `why` section from rows of `why_posts` (or any table with the columns `label`, `model_call`, `half_call` and `in_fair_comparison`): label counts and share, `too_few_bullish_bearish`, model calls and shares, calls at 0.5 with their share and its calibration, and the fair comparison with the same shares and differences. Topic rows add `topic`, `name`, `too_few_posts` and `label_vs_overall_pp` around it. |
| `why_table` | The topic × bullish table as shown in chapter 10: the row `all`, then one row per topic, most bullish first; with the shares at 0.5 and calibrated, the too-few-bullish-or-bearish mark and, in the fair comparison, both new shares and their differences from the labels; shares rounded, "—" where a share cannot be computed. The exact numbers are in `brief["why"]`. |
| `BRIEF_SCHEMA_TEXT`, `BRIEF_SCHEMA` | Chapter 11: the format rules as text, identical to `docs/brief.schema.json`, and as a dictionary. |
| `brief_problems(document)`, `validate_brief(document)` | Every way in which a brief (a plain JSON-like dictionary) breaks the rules, one line each (`<field path>: <what is wrong>`; empty when it passes), including NaN and infinite numbers; and a check that raises `ValueError` listing them. |
| `save_brief(brief, path)` | The only way the brief is saved: converts numpy and pandas values (NaN and infinity become `None`), runs `validate_brief` on the result, and writes it only when that passes (`allow_nan=False`). Returns what it wrote. |

They use nothing else from the notebook. |
| `panel` | The page built from `brief_path` in the last cell; started there when `LAUNCH_PANEL` is `True`. |

**Working sample.** Keep the classes in use (`N_CLASSES = 2` drops neutral), keep only Bitcoin posts when `BTC_ONLY`, then draw the same number of posts from every class with `RANDOM_SEED`: the smaller of `SAMPLE_PER_CLASS` and the size of the smallest remaining class. Chapter 2's statistics use `df_all`; chapter 3 cleans `df` only.

**Cleaning.** Lower case → extra whitespace → HTML tags → emoji to words (only with `EMOJI_TO_WORDS`; skin-tone qualifiers dropped, underscores turned into spaces) → special characters (keep letters, digits, whitespace) → contractions (`contractions` package; it also expands apostrophe-free forms such as "dont" and "cant", so negative contractions come back as "not") → stop words (NLTK English list, minus the negation words when `KEEP_NEGATIONS`) → WordNet lemmatisation.

**Sentiment models.** Chapter 4 only shows two tokenizers (NLTK words and a BPE tokenizer trained on the original text of the working sample); nothing from it reaches a model. Chapter 5 splits `df` 80/20 and then the 20% part half and half, both times stratified by label with `RANDOM_SEED`; every class needs at least 10 posts in the working sample, otherwise the notebook stops with a clear message. Chapter 6 fits a `CountVectorizer` and a `TfidfVectorizer` (`max_features=VOCAB_SIZE`, 32-bit floats) on the training set's `clean_text` and only transforms the validation and test sets; the matrices stay sparse instead of `.toarray()`. Chapter 7 trains one Keras network per vector type: a single `Dense` layer, with one sigmoid unit and binary cross-entropy for two classes (inside the network bearish → 0, bullish → 1) or three softmax units and sparse categorical cross-entropy for three classes (labels unchanged), Adam, `EPOCHS` and `BATCH_SIZE`, after `tf.keras.utils.set_random_seed(RANDOM_SEED)`. The validation set is watched during training and then used once to choose the model with the higher macro-F1 (a tie goes to `count_network`). Chapter 8 is the only place that evaluates on the test set; chapter 10 later scores the test posts that are also in the topic post table, only to count them, and nothing is trained or chosen after that.

**Topics.** Chapter 9 builds `topic_posts` from `df_all`: with `TOPIC_SCOPE = "btc"` every post with `mentions_btc`, with `"all"` every post; when more than `TOPIC_MAX_POSTS` posts are in scope, `DataFrame.sample(n=TOPIC_MAX_POSTS, random_state=RANDOM_SEED)` keeps that many, put back into file order. The posts are cleaned with `clean_texts`. A `TfidfVectorizer` of its own (`max_features=1000`), separate from chapter 6's, learns on the whole table (no labels, so no test set to leak into); it leaves out the negation words kept by chapter 3, "face" (the generic word of emoji names) and, with `"btc"`, "bitcoin" and "btc", because they would sit in every topic name. `KMeans(n_clusters=N_TOPICS, n_init=10, random_state=RANDOM_SEED)` groups the TF-IDF vectors; it runs in a single thread (`threadpoolctl`), because KMeans adds up its sums in several threads in a varying order, which can change the last digits and in rare cases a topic. A topic's name is the five words with the largest values in its centre; its quotes are the original texts of the three posts closest to the centre, a text already shown being skipped; only posts with at least one word of the vocabulary are quoted, unless a topic has no other posts (a post without any such word is a vector of zeros and can sit close to a centre near zero without sharing anything with the topic). With the same data source and switches, every run gives the same topics.

**Why.** Chapter 10 scores the `clean_text` of every post in `topic_posts`, neutral posts included, with `sentiment_proba` (with two classes the model never learned neutral posts, so scoring them uses the model beyond what it was trained for; the notebook says so). The probability of bullish becomes a call with `BULLISH_THRESHOLD` and `BEARISH_THRESHOLD`. For the whole topic post table and for every topic it reports the posts per label and the **bullish share by label** (bullish ÷ (bullish + bearish), neutral left out) with its difference from the whole table in percentage points; the model's calls, the **bullish share by model** (bullish ÷ (bullish + bearish) calls, unsure left out) and the unsure posts as a share of all posts; and a **fair comparison** on the posts the model never saw (`post_id` not in `train_post_ids`) that are labelled bearish or bullish: both bullish shares on those posts and the model minus the labels in percentage points. Posts whose text equals a training post but whose id differs count as unseen; how many are in the comparison is recorded. A share with a zero denominator is `null` in the brief and "—" in the table, and so is every difference computed from it. Topics are sorted by bullish share by label, highest first, `null` last, ties by topic number. A topic with fewer than `MIN_TOPIC_POSTS` posts is marked: the default 200 is a rule of thumb (if about half of a topic's posts are neutral, 200 posts leave about 100 bullish or bearish posts, and with 100 posts a share near one half can be off by about 10 percentage points by chance), not a statistical test.

**Calibration.** Counting the model's calls gives a biased share, because the model finds bullish and bearish posts differently well: if a share *t* of the bullish posts and a share *f* of the bearish posts are called bullish, a group with a true bullish share *p* shows *h* = *p* × *t* + (1 − *p*) × *f* on average. Chapter 10 therefore also splits every post at 0.5 (`half_call`), counts the **share at 0.5** *h*, and **calibrates** it: (*h* − *f*) ÷ (*t* − *f*), clipped to [0, 1]. *t* is the bullish recall and *f* is 1 − the bearish recall of the chosen model in chapter 8's evaluation table, on the test posts that match the topic posts (`test_mentions_btc` with `TOPIC_SCOPE = "btc"`, `all_test` with `"all"`); nothing is trained or evaluated again. With two classes the 0.5 split gives exactly chapter 8's labels, which the notebook checks on the test posts (with three classes, on the test posts chapter 8 called bearish or bullish); it differs from `model_call` only when both thresholds are 0.5 and a probability is exactly 0.5 (bearish here, bullish there). The calibrated share is `null` when the share at 0.5 is `null`, when a rate is `null` (`rates_missing`), when *t* − *f* is below `MIN_RATE_GAP` or not above 0 (`rate_gap_too_small`), and with three classes (`three_classes`: 1 − the bearish recall then also counts bearish posts called neutral). The calibrated share is the model's bullish share to use; the columns with the 0.3 / 0.7 thresholds stay as a comparison. Every row, the overall row included, gets the calls at 0.5, both shares and `too_few_bullish_bearish` (fewer bearish + bullish posts by label than `MIN_BULLISH_BEARISH_POSTS`; it changes no number); every fair comparison gets the same shares and their differences from the labels. A whole row's shares at 0.5 cover neutral posts too, so they are compared with the labels only in the fair comparison. The rates come from test posts, and the test posts in the topic post table are also in the fair comparison, so the calibrated share there is a little optimistic; their number is recorded (`n_rate_posts_in_fair_comparison`).

**Cache.** Chapter 1 stores `df_all`'s three loaded columns as Parquet in `{WORK_DIR}/cache/posts-<fingerprint>.parquet`. The fingerprint of a local file is a SHA-256 hash of its bytes (any edit forces a fresh read); for a web address it is a hash of the address.

### The brief

The brief has a fixed format, version **1.2**. [docs/brief-format.md](docs/brief-format.md) describes it field by field (type, whether the field is always there, whether it may be `null`, what it means), says which posts each section covers, where daily results will go and when the version changes; [docs/brief.schema.json](docs/brief.schema.json) holds the same rules as a JSON Schema. In short:

- Top level, always present: `format_version` (the version above), `generated_at` (UTC, ISO 8601), `scope`, `dataset` (chapters 0 to 3), `sentiment` (chapters 4 to 8), `topics` (chapter 9), `drawers` (chapter 9), `why` (chapter 10). Every section starts as `null` in the notebook and is filled by its chapter before the brief is saved.
- `scope`: `source` (the `DATA_SOURCE` value), `granularity` (`"batch"`: one result for the whole dataset; `"daily"` is reserved for dated data and not allowed in the current format), `coins` (`"all"` or `"btc_only"`, describing the working sample only), `n_classes`. Each section's own fields say which posts it uses: with the default switches the models learn from posts about all coins, while the topics and the topic × bullish table use only posts that mention Bitcoin.
- A value that cannot be computed (for example a share with a zero denominator) is `null`, never 0, NaN or infinity, and only the fields the format document marks "Null: yes" may be `null`. `save_brief` converts numpy and pandas values to plain values (NaN and infinity become `null`), checks the result against the rules, and writes it only when it passes; the JSON writer also refuses NaN.
- The rules allow no other fields. Adding or changing a field means changing the rules, the format document and the format version together (see [Versions](docs/brief-format.md#versions) and [Editing the notebook](#editing-the-notebook)).

## Editing the notebook

1. Edit `notebook/ledger_eyes.py` only.
2. Regenerate the notebook: `scripts/build_notebook.sh` (writes `notebook/ledger_eyes.ipynb`; cell ids come from the cell content, so an unchanged source gives a byte-identical file).
3. Run `scripts/check.sh quick`.

Changing the brief's format (a new field, a changed field): change `docs/brief.schema.json`; copy its text unchanged into `BRIEF_SCHEMA_TEXT` in chapter 11; set the new `format_version` in the rules' `const`, in the cell that creates `brief` and in `docs/brief-format.md`, following [Versions](docs/brief-format.md#versions); update the field tables of `docs/brief-format.md`. The quick check fails until the two copies of the rules are identical, the document lists exactly the fields of the rules and every brief passes them. The locked counterexamples in `scripts/check.py` may only be added to.

Writing rules for the notebook: one cell does one thing; every code cell, or short run of related code cells, is preceded by an explanation cell; explanation cells are English, then a line with `***`, then Chinese; code comments are English only. New switches go into the parameters cell in the same form, all package installs stay in the single install cell right after it, and chapter 11 (format, check, save and panel) stays the last chapter: a new chapter goes before it.

### Text rules

The quick check scans every text file in the repository outside `data/` and `.venv/` and rejects:

- private numbering, in the forms the private log uses: file-name prefixes (two digits, optionally one of the capital letters A–D or Q, optionally a round suffix `-R` or `-` plus a number, then `_W` and a week number), review codes (two digits, a capital A–D, then `-R`), `W` followed by two digits, `Q` followed by two digits, and week numbers written in Chinese. A bare "two digits and a letter" is deliberately not flagged, because it collides with normal notation such as 50D (50 days) or 10B (10 billion). Before scanning, the check tests these rules on built-in examples (`NUMBERING_MUST_MATCH` and `NUMBERING_MUST_NOT_MATCH` in `scripts/check.py`): every log code form must be caught and notation such as 50D, 30D, 7D, 10B or W2 must not be; if either fails, the check fails;
- names of chat assistants and their vendors, the two-letter capitalised abbreviation for artificial intelligence, and co-author trailers;
- local home paths and user names.

Chinese text is allowed only in the notebook's explanation cells, after the `***` line. The exact patterns are in `FORBIDDEN_PATTERNS` in `scripts/check.py`.

## The sample

`samples/stocktwits-crypto-sample.xlsx` holds 600 posts taken unchanged from the public dataset, in the same layout as the original file (sheets `stocktwits_1` and `stocktwits_2`, columns `text` and `label`), so the notebook reads it with the same code. `scripts/make_sample.py` drew it with seed 42 from `st-data-full.xlsx`: for each class (bearish, neutral, bullish) 80 posts that mention Bitcoin, 20 other posts with emoji, 20 other posts with a negation and 80 other posts, 200 per class. Rows keep their original sheet and order. Posts that read as empty (the formula cells described below), start with `=` or contain characters a spreadsheet cannot store were skipped, so the sample contains no formula cells.

Source: [ElKulako/stocktwits-crypto](https://huggingface.co/datasets/ElKulako/stocktwits-crypto) on Hugging Face, released under the MIT License. For academic use the dataset author asks to cite <https://ieeexplore.ieee.org/document/10223689>.

## Known limitations

- **59 posts lose their text.** In `st-data-full.xlsx`, 59 posts begin with `=`, so the spreadsheet stores them as formulas whose stored value is an error such as `#NAME?` (for example row 365284 of `stocktwits_1`, originally "=the new btc"). pandas, on Colab as well as locally, reads these cells as empty, so they appear in `df_all` as empty strings with their labels intact and are counted in `n_empty_text`. That is 59 of 1,331,697 posts; the notebook keeps them as they are rather than reading the file a second way. Five of them mention Bitcoin, so the Bitcoin count is 5 lower than it would be with the original text.
- The notebook has not been run on Colab itself yet, so neither has the panel: whether Gradio shows it inside Colab without a public link is untested.
- Training is seeded, but TensorFlow does not promise bit-identical results across runs and machines, so model scores (and, when the two are close, the chosen model) may differ slightly. Counts and the two baseline rows do not depend on training.

## Data policy

The full dataset and everything computed from it (caches, executed notebooks, briefs, tables and quotes produced from the full data) stay in `data/`, which Git ignores. They are never committed, also not in this README or in `docs/`. Only the sample above and examples produced from the sample (or written by hand) may be committed; the examples in `docs/brief-format.md` are written by hand.
